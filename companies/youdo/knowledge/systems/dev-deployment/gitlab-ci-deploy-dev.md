## Parameters and access

- `SERVICE` is populated from `CI_PROJECT_NAME`.
- `VERSIONS` uses the Jenkins pipeline contract `service|project_id|type|key|`: merge-request pipelines send `mr` with `CI_MERGE_REQUEST_IID`; other pipelines send `branch` with `CI_COMMIT_REF_NAME`.
- Decision confirmed on 2026-08-20: GitLab does not pass `APP_IMAGE_TAG`; Jenkins remains responsible for deriving the image tag from the supplied MR or branch and its GitLab pipeline metadata.
- Jenkins authentication uses the fixed service-account name `technical` and the protected/masked GitLab CI/CD variable `JENKINS_TECHNICAL_TOKEN`; its value is not stored in this note. The job obtains and sends a Jenkins crumb.
- `JENKINS_URL` and `JENKINS_DEPLOY_DEV_JOB` can be overridden through higher-precedence GitLab variables.
- After triggering `buildWithParameters`, the job reads the Jenkins queue URL from the `Location` response header, polls the queue until an executable build is assigned, and polls that build until completion.
- Only Jenkins result `SUCCESS` is accepted. `FAILURE`, `UNSTABLE`, `ABORTED`, queue cancellation, API errors, and polling timeouts fail the GitLab job.
- Polling uses `JENKINS_POLL_INTERVAL=10` seconds by default and can be configured through a GitLab variable. Overall waiting is bounded by the GitLab job timeout.

## Dev environment lifecycle jobs (added 2026-08-20)

- `1 deploy dev` registers the dynamic GitLab environment `dev/$CI_PROJECT_PATH_SLUG-$CI_PIPELINE_ID`, associates `3 delete dev` as its stop action, and sets `auto_stop_in: 7 days`.
- `2 extend dev` is manual. It verifies that the target namespace has `createdBy=jenkins` and `environment=dev`, sets `k8s-ttl-controller.twin.sh/ttl=5d`, updates `k8s-ttl-controller.twin.sh/refreshed-at` to current UTC time, and resets the GitLab environment auto-stop period to five days with `action: access`.
- `3 delete dev` is both a manual environment stop action and the action automatically invoked by GitLab after `auto_stop_in`. It checks the ownership labels before deletion and treats an already absent namespace as success.
- Both lifecycle jobs use the `KUBECONFIG_DEV` GitLab CI/CD variable. The template accepts either raw kubeconfig YAML or a GitLab file-variable path, writes/copies it to `~/.kube/config`, and sets mode 0600. GitLab variable type `File` is preferred. The credential value is not stored here. For the pilot MR the variable cannot be protected unless the source/target refs are protected, otherwise GitLab will not expose it to the job.
- The deploy dotenv artifact is retained for one month so the automatic stop action can recover the namespace name after extensions.
- GitLab `action: access` auto-stop resetting requires GitLab 17.7 or later. The internal `/api/v4/version` request returned HTTP 401 with the locally available token on 2026-08-20, so server-version compatibility still requires CI lint or a smoke pipeline.
- The Helm chart already adds a default namespace TTL of seven days. The `k8s-ttl-controller` repository defines `refreshed-at` as the timestamp from which TTL is recalculated; the local `infra-tf` checkout did not contain a controller installation when checked on 2026-08-20, so GitLab `on_stop` is currently the explicit deletion path and the Kubernetes annotations are controller-compatible lifecycle metadata.

## Second iteration: task-based namespaces (prepared 2026-08-25)

- Jenkins is the sole source of the Kubernetes namespace name. For an MR selection it searches the MR title first and its source branch second; for a branch selection it searches the branch. Recognized case-insensitive task IDs are `Site-<digits>`, `DevOps-<digits>`, and `AP-<digits>`. The ID is lowercased; if no ID is found, a lowercase DNS-safe branch slug is used. The `dev-` prefix is retained and the generated deploy ID is limited to 59 characters so the full namespace remains within 63 characters. Examples: `DevOps-689-k8s` -> `dev-devops-689`, MR title `[AP-435] Add feature` -> `dev-ap-435`, `feature/My_Long.Branch` -> `dev-feature-my-long-branch`.
- The Jenkins UI no longer offers `master` for the primary service. Runtime validation also rejects a missing primary selection, direct `branch|master` parameters, and an MR whose resolved source branch is `master`; dependent services can still default to master.
- Jenkins archives `generated/deploy-dev.env` with `DEV_NAMESPACE` and `JENKINS_BUILD_NUMBER`. GitLab waits for Jenkins success, downloads this authenticated artifact, validates both values, and publishes them in its own dotenv report. GitLab no longer reconstructs a namespace from the Jenkins URL/build number.
- The namespace chart keeps the real Jenkins `BUILD_NUMBER` in label `jenkinsJobId`, while task/branch deploy ID drives namespace, service releases, routing, and host names. Lifecycle jobs verify the returned build number against this label, preventing an old pipeline from extending or deleting a namespace that a newer Jenkins build has updated.
- GitLab environment names and resource groups now use `dev/$CI_PROJECT_PATH_SLUG-$CI_COMMIT_REF_SLUG`, fixing the unsupported/empty `CI_PIPELINE_ID` expansion and serializing lifecycle jobs for the same ref. Jenkins job `test` itself currently allows concurrent builds and the Lockable Resources plugin is not installed; different refs that resolve to the same task ID remain a concurrency edge case to monitor.
