# Git corrections: subsequent-task application audit

## Summary
This audit answers the user's question about application of corrections, superseding the interpretation of the earlier publication comparison as proof of learning. Seven correction families were traced from original evidence to their saved instructions and later applicable work. Three have observed application in later distinct tasks: checkout preservation, branch/MR conventions, and master-based base-image releases. Scope expansion recurred. Local-build and clickable-MR-link corrections were applied within continuing work, without proof of transfer into an independent session. Training bookkeeping failed: the prospective counter remained zero and no formal outcome evaluations existed before this audit.

The observed behavior supports partial application of saved corrections, not reliable learning across all agents or a causal proof that a retrieved rule produced each success. Historical rule-read/session evidence is unavailable. A green pipeline, accepted MR name, saved rule or lack of complaints is not itself a learning result.

## Diagnosis
**Saving:** canonical rules for checkout preservation, naming, release sources and scope are present. Local-build and comment-link requirements are deliberately task-scoped. Promoting them indiscriminately to global rules would misrepresent the user's instructions.

**Retrieval/read:** historical task notes do not generally record that a specific canonical section was read before each action. The audit can confirm a saved rule and later conforming behavior, but cannot attribute the behavior to rule retrieval. For the scope failures, not-read versus violated-after-read remains unknown; do not invent a root cause from the existence of the rule alone.

**Application:** three correction families have later distinct-task examples, two have within-task application, and scope expansion recurred. These are seven reviewed families with different scopes and evidence strength, not a calculated learning success rate.

**Measurement:** zero registered evaluations before this audit and the unmaintained 0/5 establish a concrete gap between recording instructions and evaluating their use. The counter was a Markdown record that agents failed to update; saying an automatic counter broke would be inaccurate. The earlier assistant conclusion that the learning mechanism works was broader than the evidence.

**Current response failure:** after the user questioned learning, the assistant kept explaining the proposed audit. Those replies did not implement the audit. This report is the actual requested check; no automatic follow-up mechanism is claimed.

## Follow-up: does agent_learning itself work?
The user requested checking the tool itself after the application audit. Read agent_learning.py record/query/verify/report implementations and existing test coverage. All 15 existing test_agent_learning.py tests passed using temporary stores, including deduplication, scope/task isolation, corruption handling, explicit truncation, revision-aware evaluations and concurrent writers. The real-store check validated all27records. These checks establish the tested storage/retrieval/accounting behavior, not agent compliance.

record saves evidence; link-rule references the canonical instruction without editing it; query filters and prints records but does not load target files into an agent or enforce their use. Non-global records use literal AND keyword matching, exact system filtering and explicit task/repo selectors. Active global rules bypass keyword/system filters and output is limited, with a truncation notice; an agent must inspect that notice and retrieve omitted relevant entries. This is a deterministic retrieval helper rather than semantic task understanding.

verify appends the caller-supplied outcome and rule-loaded flag. It does not inspect transcripts, source artifacts or actions to establish whether pass/fail is true. report calculates statistics only from those supplied outcomes; it neither discovers missing applicable tasks nor checks whether the observation ledger is current. The current1/1 is the single retrospective preservation evaluation added during this audit, with rule-loaded unknown. It is not a learning success rate for all work. Before that write the count was zero.

No background evaluator or automatic rule enforcement is implemented by these commands. Correct usage depends on agents recording, retrieving, reading canonical targets and honestly evaluating applicable outcomes. Thus the tested CLI works, while the complete ongoing correction-to-behavior evaluation process was not maintained. No source, skill or settings fixes were implemented in this follow-up; the existing central proposal remains the only optional implementation action.
